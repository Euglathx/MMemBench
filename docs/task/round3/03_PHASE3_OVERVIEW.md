# Phase 3: 严格验证方案概述

## 目标

对Phase 2的所有修复进行可量化的验证，确保问题不再出现。

## 验证原则（零容忍）

1. **任何维度失败 = 整体FAIL**
2. **必须有明确的数值阈值**（不接受"基本正确"）
3. **边界case必须覆盖**
4. **回归检测：修复前vs修复后对比**
5. **人工可审查：详细日志和失败原因**

## 验证脚本设计

### 3.1 图像发送完整性测试

```python
# 验证指标:
# - images_sent不为空的比率 = 100%
# - 图像文件实际存在的比率 = 100%
# - API payload包含正确image_url = 100%

# 阈值:
# - 任何一项 < 100% → FAIL
```

### 3.2 评分公式正确性测试

```python
# 验证指标:
# - LLM Judge满分(10/10) → final score >= 0.9
# - LLM Judge不及格(<=3/10) → final score <= 0.3
# - 误差率 < 5%

# 测试cases:
# - 全满分case: 预期score=1.0, 误差<0.05
# - 全低分case: 预期score<0.3
# - 混合case: 按公式计算，误差<0.05
```

### 3.3 Turn-level Ground Truth覆盖测试

```python
# 验证指标:
# - 所有中间phase的turn有独立expected_answer = 100%
# - expected_answer与turn的question对齐 = 100%
# - 不再使用task-level answer评估中间turn

# 抽查:
# - 随机抽取50个ABR任务的turn 2
# - 验证expected_answer != task final answer
```

### 3.4 Simulator真值一致性测试

```python
# 验证指标:
# - "伪确认"率 = 0%（模型错误不应被肯定）
# - 错误传播率 < 5%（容忍极少数边界case）
# - Consistency check基于ground truth = 100%

# 测试:
# - 创建10个故意错误的模型responses
# - 验证simulator不会说"you correctly..."
```

### 3.5 多图任务端到端测试

```python
# 验证指标:
# - AC任务定义一致性 = 100%
# - images_sent与question target对齐 = 100%
# - Evaluator知道实际发送的图像 = 100%

# 测试cases:
# - 单图任务: 只发送1张
# - 3图任务: 根据策略发送
# - 渐进式任务: 逐张发送
```

### 3.6 评估器状态一致性测试

```python
# 验证指标:
# - 同一任务内对同一物体的判断一致性 >= 95%
# - 所有维度分数的动态范围 > 0.3（不能是常数）
# - 默认值保留率 < 20%（大部分应该被更新）

# 测试:
# - 运行20个任务
# - 对每个任务的所有turn，检查判断一致性
```

### 3.7 回归测试套件

```python
# 对比修复前后:
# 1. 运行相同的100个任务
# 2. 对比评估结果:
#    - 是否更合理？
#    - 是否减少误判？
#    - 是否减少矛盾？

# 必须改进的指标:
# - 图像发送率: 0% → 100%
# - 评分合理性: 提升至少30%
# - 判断一致性: 提升至少20%
```

## 验证报告格式

每个测试必须输出：

```json

  "metrics": {

    "metric_2": {"value": 1.0, "threshold": 1.0, "pass": true}

  "overall_pass": false,
  "failure_reasons": ["metric_1 below threshold: 0.95 < 1.0"],
  "evidence": {
    "failed_cases": [...],
    "sample_logs": [...]
  }
}
```

## 成功标准

### Phase 3整体成功：

- [ ] 所有7个测试100% PASS
- [ ] 所有指标都达到阈值
- [ ] 回归测试显示显著改进
- [ ] 生成的改进报告可量化

### 单个测试PASS条件：

- **所有**核心指标达到阈值（不是"大部分"）
- 没有严重的失败cases（边界case可以标记为已知限制）
- 报告清晰、可复现

## 失败处理

如果Phase 3测试FAIL：

1. **回到Phase 2修复**（不是调整阈值！）
2. **分析失败原因**
3. **修改代码**
4. **重新运行测试**
5. **直到100% PASS**

**不允许的做法**：
- ❌ 降低阈值来"通过"测试
- ❌ 删除失败的test cases
- ❌ 标记为"已知问题"然后跳过
